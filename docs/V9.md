# V9 Local Hardening

Box only (no VPS/Cloudflare). pi 1.4.0, real model via a native provider, Playwright MCP.
Test dir `/tmp/pimu-v9`, data dir `/tmp/pimu-data`, `PIMU_MAX_JOBS=2` for item 2+.
Screenshots: `/workspace/pimu-shots/v9-*` (not in the repo).

## Stage 1: security + tests

- Internal API needs a per-session capability (`X-Pimu-Cap`), scoped to
  {session, bot, goal, job}. Pimu writes it to a 0600 file; the extension reads it,
  unlinks it and drops the env var, so `bash` never sees it. The server token is no
  longer passed to any child. Pimu scrubs `PIMU_*` from its own env and sets
  `PR_SET_DUMPABLE=0`.
- Approvals: hash = bot + goal + job + tool + canonical args, computed server-side;
  approved → claimed once (`used`, with `used_by`); denied holds 24h; pending 24h,
  approved 2h, then `expired`; restart expires waiting ones. Status lookups are
  checked against the caller's scope.
- Gate (`extensions/pimu-agent.ts`): `/proc/`, secret paths and other bots' data dirs
  blocked at every level (realpath'd); strict read-only bash allowlist; dangerous
  commands hard-blocked in jobs; nested tool calls go through the same handler.
- `go test ./...`: 38 top-level tests, 0 failures. Fake pi (`internal/fakepi`, the test
  binary re-execs itself as pi) covers RPC, jobs (complete/fail/queue/cancel/steer/
  interrupted), goals (precheck, rate, auto-disable, actions, prompt), approvals
  (lifecycle, TTL, 8-way claim race), internal API auth/scope, caps, scrub, and the TS
  gate run under node with a fake API.

## Remaining risks

- Same uid can read the pi (node) process memory, so a job's cap is readable there;
  it only grants that session's own scope.
- Bot main sessions are ungated by design (only secret paths are blocked); they can
  run any bash (e.g. `find /`).
- A later extension could mutate `tool_call.input` after the gate.
- The worker cannot tell that it waited for approval (it reported "不需要人工批准").
- Not verified: iPhone Safari, Telegram, very long gate waits, daily token cap.
